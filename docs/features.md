# ContractGuard AI — Feature List

ContractGuard AI is a local-first, agentic tool that turns an OpenAPI
contract change into an evidence-backed migration plan and a validated,
human-approved remediation — not just a diff report. Deterministic tools
stay authoritative for every fact (diffs, evidence, Git state, patches, test
results); the LLM explains, investigates, plans and proposes code within a
bounded, schema-validated loop it can never bypass.

---

## 1. Contract Analysis

- **Deterministic OpenAPI 3.x diff** between an old and new specification —
  no LLM involved in detecting a change, only in explaining it.
- **Fixed-policy classification** of every change as `BREAKING`,
  `POTENTIALLY_BREAKING`, `NON_BREAKING`, or `UNKNOWN`.
- Detects endpoint renames/removals, request/response schema field renames,
  removals and additions, and enum value removals.
- Every classification is paired with a plain-language explanation of the
  consumer-facing consequence, generated by the LLM strictly from the facts
  the deterministic diff already produced — it cannot add or remove changes.
- An **instant preview** on the New Run form shows the classified change
  count and breakdown the moment both specifications are picked — before
  committing to a full run, no repository needed, no LLM call, zero cost.

## 2. Consumer Impact Analysis

- **Agentic evidence search**: the LLM investigates a real consumer
  repository within a bounded tool loop (search, read file, list directory)
  to find every usage a contract change actually affects.
- Every reported impact carries **file-and-line evidence** — no impact
  claim is accepted without a citation back to real source code.
- Severity and confidence are assessed per affected component, with the
  failure mode spelled out (e.g. "deserialised field is null").

## 3. Migration Planning & Governance

- Generates a structured **migration plan**: objective, expected files,
  proposed action, tests to update, validation command, risk, rollback —
  per plan item, all evidence-linked.
- **Human approval is mandatory** before any source modification. Approval
  is bound to an exact **plan hash**; approving a stale or mismatched plan
  is rejected outright (`APPROVAL_MISMATCH`).
- A full **audit trail** records every state transition, approval decision
  and repository mutation with principal, timestamp, run ID and plan hash —
  independent of run retention, so it survives even after a run is purged.
  Viewable per-run and as an org-wide, filterable **Audit log** page.

## 4. Automated Remediation

- Creates an **isolated Git branch** before touching anything; the original
  branch is never mutated directly.
- Applies a **minimal, approved-files-only patch** — the agent cannot touch
  a file outside what the approved plan named.
- Permits **at most one bounded repair attempt** if validation fails after
  the first patch, never an open-ended retry loop.
- Every mutation path is gated by the same safety invariants: approval
  first, plan-hash binding, approved-files-only, bounded repair, secret
  redaction.

## 5. Build & Test Validation

- Runs the consumer's own test suite (Maven wrapper) to confirm the
  remediation actually compiles and passes.
- **Sandboxed validation** (opt-in): builds run in a resource-limited
  container — bounded CPU, memory and wall-clock, no network egress by
  default (dependencies are read from a mounted local cache instead of
  granting network access).

## 6. Reporting & Audit

- Auditable **Markdown and JSON reports** per run: changes, evidence,
  assessments, plan, patches, validation results.
- A **live timeline** streams every step as it happens (tool call, LLM
  reasoning, human decision, system event), tagged by who acted.
- A **git-style diff viewer** with syntax highlighting shows exactly what
  the remediation changed, file by file.

## 7. Source Management

- **Local workspace repositories** — zero-config, filesystem-based, for
  bundled or manually placed consumer checkouts.
- **Registered GitHub repositories** — clone/fetch over HTTPS with an
  encrypted-at-rest personal access token; no pre-existing local checkout
  required.
- **Registered spec-source repositories** — a second, read-only
  registration kind for OpenAPI specs living in their own repository; the
  token is optional since most spec repositories are public.
- **Direct specification upload** — drop a `.yaml`/`.yml`/`.json` file in
  through the dashboard with no repository at all.
- All three specification origins (bundled, uploaded, spec-source) land in
  one combined picker, disambiguated by a qualified ID so same-named files
  from different sources never collide.
- **Deregistration** for every registered kind (repository, spec source,
  upload) — removing a repository or spec source also clears its local
  clone cache, so a corrected re-registration never reuses a stale checkout.
- A dedicated **Settings** page keeps registering/removing sources fully
  separate from starting a run — no wizard, no back-and-forth.

## 8. Remote Git Integration & Publishing

- Clones and refreshes registered GitHub repositories automatically —
  everything downstream (diff, evidence search, execution) works exactly as
  it does for a local workspace repository.
- **One-click publish**: commits the working branch, pushes it, and opens a
  **draft pull request** whose body embeds the plan hash and links evidence
  back into the target repository — a distinct, explicit action, never
  automatic.
- A failed publish (e.g. an expired token) can be **retried** once the
  underlying issue is fixed, without re-running analysis or execution.

## 9. CI/CD Integration

- A **headless CLI** runs analysis only (no remediation) against two specs
  and a consumer checkout, emits a JSON report, and exits non-zero on
  breaking changes above a configurable severity threshold.
- Ready-made **GitHub Action** and **GitLab CI** templates so a provider's
  pull request that edits an OpenAPI spec fails fast with the impact table
  posted as a PR comment.

## 10. Persistence & Reliability

- Durable **PostgreSQL** (or embedded H2 for local/single-node use) storage
  behind a stable repository abstraction, schema-managed with Flyway
  migrations from day one.
- A **bounded run queue** with per-repository mutual exclusion — no two
  runs mutate the same repository at once.
- Runs interrupted by a restart **resume cleanly** from the last safe
  persisted state, or finalise as `FAILED` with a clear remediation message
  — never left stuck in limbo.
- Configurable **retention policy** for finished runs and their artifacts.

## 11. Observability

- **OpenTelemetry traces** spanning every pipeline step, nested under a
  phase-level span (analyse/execute/publish), with LLM calls annotated by
  token count.
- **Prometheus metrics**: runs by state, per-step durations, LLM token
  spend.
- Health and readiness probes for orchestration.
- The bundled Docker demo ships a **Jaeger trace viewer** out of the box —
  nothing to configure to see a real trace.

## 12. LLM Provider Flexibility

- Runs behind a provider-agnostic `LlmGateway` abstraction.
- **Deterministic mock mode** by default — the entire product, including
  the bundled demo, runs with no API key and no network calls, fully
  reproducible for tests and evaluation.
- **OpenAI-compatible endpoint support** (any provider implementing the
  `/chat/completions` contract) via three configuration values: base URL,
  API key, model — no code changes needed to switch.

## 13. Deployment & Operations

- **One-command Docker deployment** (`docker compose up --build`) — backend,
  frontend, and a bundled Jaeger trace viewer, healthchecked and networked
  together.
- Every optional feature (real LLM, remote-repository credential key, audit
  principal, trace destination, bundled demo content) is a single `.env`
  value — the base deployment needs none of them set.
- An opt-out for the bundled demo repository/specs
  (`CONTRACTGUARD_DEMO_CONTENT=false`) once real sources are registered, so
  the picker only shows what you actually configured.

## 14. Dashboard Experience

- A **statistics dashboard**: run activity over time, outcome and
  classification breakdowns, change-type distribution, remediation
  first-pass/repair rates and lines-of-code touched — all computed
  server-side from the persisted run history (`GET /api/statistics`) and
  rendered as dependency-free SVG charts whose segment ordering was
  validated for colour-vision-deficiency separation.
- A **filterable run history** page with per-run detail views at stable,
  shareable URLs (`/runs/{id}`).
- A **single-panel run form** — pick repository, old spec, new spec, name,
  go — with no forward/back navigation.
- A **Run again** button on every run's detail page, pre-filling New Run
  with the exact same repository and specification versions.
- A **Settings** page holding all source registration/upload/removal,
  the light/dark theme choice, and the quick reference.
- A first-run **onboarding banner** naming the three-step workflow, and an
  in-app **quick-reference panel** for anyone who gets lost mid-workflow.
- A site-wide **notification** the moment any run needs attention (awaiting
  approval, succeeded, failed, or failed to publish), wherever the dashboard
  is open — clicking one jumps straight to the exact section to act on.

## 15. Notifications

- A run reaching a state needing human attention raises an **in-app toast**
  from anywhere in the dashboard, deep-linking to the exact section to act
  on (approve, publish, or see why it failed) with a brief highlight so it's
  obvious where the page landed.
- The same signal can also fire an **outbound webhook** — a Slack-incoming-
  webhook-compatible JSON payload — so a team doesn't have to keep the
  dashboard open. Off by default; a single URL enables it.
- Delivery is **asynchronous and best-effort**: a slow or unreachable
  endpoint never adds latency to the run, and a failed delivery is logged,
  never retried — the audit trail and dashboard remain the durable record.

## Current boundaries

Honesty about what isn't built yet is part of the product:

- **Language/build support**: Java 21 / Spring Boot consumers with Maven
  today; Gradle and TypeScript/JavaScript consumers are on the roadmap.
- **Remote hosting**: GitHub over HTTPS with a personal access token only —
  no GitLab, Bitbucket, or SSH yet.
- **Identity**: single-operator trust model — no authentication, SSO, or
  per-user role separation yet (every action is attributed to one
  configured principal).
- **Notifications**: a generic outbound webhook covers Slack (and anything
  else that accepts a JSON POST) today; no email delivery or per-repository
  configuration yet.
- **Fleet intelligence**: no org-wide consumer registry, watch mode, or
  blast-radius dashboard yet — each run analyses one API change against one
  consumer at a time.
- **No autonomous merge** — a human always merges the resulting pull
  request; ContractGuard never does it for them.
